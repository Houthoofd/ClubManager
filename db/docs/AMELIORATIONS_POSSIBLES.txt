1️⃣  AJOUTER SOFT-DELETE SUR TABLES CRITIQUES
────────────────────────────────────────────────────────────────────
📌 Problème: 20+ tables sans colonne deleted_at
📊 Impact: Perte de données définitive lors des suppressions
⚡ Effort: 1 heure
💰 Gain: RGPD compliance, traçabilité, récupération possible

Tables prioritaires à modifier:
  • payments (CRITIQUE - historique financier)
  • bookings (réservations clients)
  • direct_messages (communications)
  • alert_types (données de référence)
  • article_categories (catalogue)

Script:
  ALTER TABLE payments ADD COLUMN deleted_at TIMESTAMP NULL;
  ALTER TABLE payments ADD COLUMN deleted_by INT NULL;
  CREATE INDEX idx_payments_deleted ON payments(deleted_at);

2️⃣  VUES MATÉRIALISÉES POUR DASHBOARDS
────────────────────────────────────────────────────────────────────
📌 Problème: Requêtes lourdes de dashboards recalculées à chaque fois
📊 Impact: Performance dashboards (-80% temps de chargement)
⚡ Effort: 2 heures
💰 Gain: UX améliorée, moins de charge serveur

Vues à créer:
  • v_dashboard_stats (stats temps réel)
  • v_monthly_revenue (revenus mensuels)
  • v_active_students_by_sport (élèves actifs)
  • v_course_attendance_rate (taux de présence)
  • v_payment_status_summary (statut paiements)

Exemple:
  CREATE VIEW v_dashboard_stats AS
  SELECT
    (SELECT COUNT(*) FROM users WHERE deleted_at IS NULL) as total_users,
    (SELECT COUNT(*) FROM enrollments WHERE statut='active') as active_enrollments,
    (SELECT SUM(montant) FROM payments WHERE MONTH(date_paiement)=MONTH(NOW())) as monthly_revenue,
    (SELECT COUNT(*) FROM course_instances WHERE date_cours >= CURDATE()) as upcoming_courses;

3️⃣  INDEX PARTIELS (FILTERED) SUR deleted_at
────────────────────────────────────────────────────────────────────
📌 Problème: Index incluent les lignes supprimées (inutile)
📊 Impact: +15-20% performance requêtes actives
⚡ Effort: 30 minutes
💰 Gain: Index plus petits, queries plus rapides

Script (MySQL 8.0+):
  -- Créer des index qui excluent les lignes supprimées
  CREATE INDEX idx_users_active ON users(id, email)
    WHERE deleted_at IS NULL;

  CREATE INDEX idx_events_active ON events(id, start_date)
    WHERE deleted_at IS NULL;

Note: Améliore significativement les queries sur données actives

4️⃣  STORED PROCEDURES POUR OPÉRATIONS COMPLEXES
────────────────────────────────────────────────────────────────────
📌 Problème: Logique métier complexe dans le code applicatif
📊 Impact: Performance, maintenance, atomicité
⚡ Effort: 4-6 heures
💰 Gain: Code plus propre, moins de bugs, transactions atomiques

Procédures à créer:

a) sp_enroll_student(user_id, course_id)
   → Inscription + vérification capacité + notification

b) sp_process_payment(payment_id)
   → Validation + update statut + génération reçu + email

c) sp_create_recurring_instances(recurring_id, start_date, end_date)
   → Génération automatique des cours

d) sp_calculate_attendance_rate(user_id, sport_id)
   → Calcul taux de présence

Exemple:
  DELIMITER $$
  CREATE PROCEDURE sp_enroll_student(
    IN p_user_id INT,
    IN p_course_id INT
  )
  BEGIN
    DECLARE v_capacity INT;
    DECLARE v_current INT;

    START TRANSACTION;

    -- Vérifier capacité
    SELECT capacite_max, nombre_inscrits
    INTO v_capacity, v_current
    FROM course_instances WHERE id = p_course_id;

    IF v_current >= v_capacity THEN
      SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'Course is full';
    END IF;

    -- Inscrire l'étudiant
    INSERT INTO enrollments (utilisateur_id, cours_id, statut)
    VALUES (p_user_id, p_course_id, 'active');

    -- Incrémenter compteur
    UPDATE course_instances
    SET nombre_inscrits = nombre_inscrits + 1
    WHERE id = p_course_id;

    COMMIT;
  END$$
  DELIMITER ;

5️⃣  VALIDATION / NORMALISATION DES COLONNES JSON
────────────────────────────────────────────────────────────────────
📌 Problème: 19 colonnes JSON sans validation de structure
📊 Impact: Risque de données incohérentes
⚡ Effort: 3-4 heures
💰 Gain: Qualité des données, moins de bugs

Tables concernées:
  • events: categories, belt_levels
  • api_keys: scopes, allowed_ips
  • email_campaigns: target_segment
  • venues: facilities

Solutions possibles:

Option A) JSON Schema validation (côté application)
Option B) MySQL 8.0.17+ JSON validation avec CHECK constraints
Option C) Normaliser en tables relationnelles (RECOMMANDÉ!)

Exemple normalisation:
  -- Au lieu de: events.categories JSON
  -- Créer:
  CREATE TABLE event_categories (
    id INT PRIMARY KEY AUTO_INCREMENT,
    event_id INT NOT NULL,
    category_name VARCHAR(100) NOT NULL,
    FOREIGN KEY (event_id) REFERENCES events(id)
  );

Avantages: requêtes plus rapides, intégrité garantie, index possibles

6️⃣  ARCHIVAGE AUTOMATIQUE DES DONNÉES ANCIENNES
────────────────────────────────────────────────────────────────────
📌 Problème: Tables deviennent volumineuses avec le temps
📊 Impact: Performance dégradée sur tables principales
⚡ Effort: 3 heures
💰 Gain: Base principale légère, queries rapides

Tables à archiver (> 6-12 mois):
  • sessions (expirées) → sessions_archive
  • api_key_usage_logs (> 3 mois) → api_logs_archive
  • login_attempts (> 1 mois) → security_logs_archive

Note: audit_logs, emails, email_queue ont déjà leur archive ✅

Script Event MySQL:
  CREATE EVENT archive_old_sessions
  ON SCHEDULE EVERY 1 DAY
  DO BEGIN
    -- Archiver
    INSERT INTO sessions_archive
    SELECT * FROM sessions
    WHERE expires_at < DATE_SUB(NOW(), INTERVAL 7 DAY);

    -- Nettoyer
    DELETE FROM sessions
    WHERE expires_at < DATE_SUB(NOW(), INTERVAL 7 DAY);
  END;

📊 Impact: UX recherche grandement améliorée
⚡ Effort: 2 heures

Tables candidates:
  • events (title, description)

  • users (nom, prenom)
  • direct_messages (contenu)

Script:
  ALTER TABLE events
  ADD FULLTEXT INDEX ft_events_search (title, description);

Usage:
  SELECT * FROM events
  WHERE MATCH(title, description)
  AGAINST ('karate competition' IN NATURAL LANGUAGE MODE)
  ORDER BY MATCH(title, description)
  AGAINST ('karate competition') DESC;

8️⃣  TRIGGERS POUR AUDIT AUTOMATIQUE
────────────────────────────────────────────────────────────────────
📌 Problème: Audit logs doivent être créés manuellement
📊 Impact: Traçabilité complète automatique
⚡ Effort: 4 heures
💰 Gain: 100% audit sans code applicatif, RGPD++

Triggers à créer:
  • users: AFTER INSERT/UPDATE/DELETE
  • payments: AFTER UPDATE
  • enrollments: AFTER INSERT/DELETE

Exemple:
  DELIMITER $$
  CREATE TRIGGER trg_users_audit_update
  AFTER UPDATE ON users FOR EACH ROW
  BEGIN
    INSERT INTO audit_logs (
      event_type,
      user_id,
      details,
      severity,
      timestamp
    )
    VALUES (
      'USER_UPDATED',
      NEW.id,
      JSON_OBJECT(
        'old_email', OLD.email,
        'new_email', NEW.email,
        'old_status', OLD.statut_id,
        'new_status', NEW.statut_id
      ),
      'INFO',
      NOW()
    );
  END$$
  DELIMITER ;

9️⃣  TABLE PARTITIONING POUR GROS VOLUMES
────────────────────────────────────────────────────────────────────
📌 Problème: Préparation pour scale (10k+ users)
📊 Impact: Maintenance facilitée, performances futures
⚡ Effort: 6-8 heures
💰 Gain: Ready pour croissance massive

Candidates au partitioning BY RANGE (date):
  • audit_logs (par mois)
  • emails (par trimestre)
  • api_key_usage_logs (par semaine)

Exemple:
  ALTER TABLE audit_logs
  PARTITION BY RANGE (YEAR(timestamp) * 100 + MONTH(timestamp)) (
    PARTITION p202401 VALUES LESS THAN (202402),
    PARTITION p202402 VALUES LESS THAN (202403),
    PARTITION p202403 VALUES LESS THAN (202404),
    ...
    PARTITION pmax VALUES LESS THAN MAXVALUE
  );

Avantages:
  - Suppression de partitions entières ultra-rapide
  - Queries sur période récente ne scannent qu'une partition
  - Backup/restore par partition possible

🔟  READ REPLICAS / CLUSTERING (Infrastructure)
────────────────────────────────────────────────────────────────────
📌 Problème: Scalabilité horizontale
📊 Impact: Haute disponibilité, load balancing
⚡ Effort: 1-2 jours (configuration infra)
💰 Gain: Zero downtime, performance x2-3

Architecture recommandée:

  [APPLICATION]
       |
       v
  [ProxySQL / MySQL Router]
       |
       +-- MASTER (writes)
       |
       +-- REPLICA 1 (reads - dashboards)
       |
       +-- REPLICA 2 (reads - API)

Setup minimal:
  1. Configurer la réplication MySQL (master-slave)
  2. Installer ProxySQL pour routing intelligent
  3. Application: pas de changement de code!

Note: Pas urgent pour TFE mais excellente connaissance à avoir
