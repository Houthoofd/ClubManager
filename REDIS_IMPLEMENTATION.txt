FONCTIONNALITÉS IMPLÉMENTÉES
================================================================================

✅ 1. REDIS CLIENT SINGLETON
   - Connexion automatique avec retry strategy
   - Health checks et monitoring
   - Graceful shutdown handlers
   - Event logging (connect, ready, error, close)
   - Connection pooling et timeout management

✅ 2. CACHE SERVICES

   A) Cache Service de Base (cache.service.ts)
      - get/set/delete opérations
      - mget/mset (opérations batch)
      - getOrSet (cache-aside pattern)
      - increment/decrement (compteurs)
      - Sets (addToSet, removeFromSet, getSetMembers)
      - Sorted Sets (leaderboards, rankings)
      - Distributed locks (acquireLock, releaseLock)
      - Pattern deletion (deletePattern)
      - TTL management (getTTL, expire)
      - Cache statistics (hits, misses, hit rate)

   B) Tenant Cache Service (tenant-cache.service.ts)
      - Cache tenant data par ID et subdomain
      - Tenant configuration et settings
      - Tenant limits et quotas
      - API call tracking par tenant
      - Tenant features flags
      - Active tenants set
      - Tenant users count
      - Cache warm-up pour tenants

   C) User Cache Service (user-cache.service.ts)
      - User profile caching
      - User permissions par tenant
      - User sessions management
      - User preferences
      - Active sessions tracking
      - Online/offline status
      - User tokens (JWT, refresh)
      - Batch operations (multiple profiles)

   D) Rate Limiter Service (rate-limiter.service.ts)
      - Token bucket algorithm
      - Sliding window algorithm
      - Rate limiting par IP, tenant, user, API key
      - Auth rate limiting (strict)
      - Webhook rate limiting
      - Whitelist/blacklist management
      - Custom rate limit options

✅ 3. MIDDLEWARES EXPRESS

   A) Rate Limiting Middleware
      - rateLimitByIp()      → Limite par IP
      - rateLimitByTenant()  → Limite par tenant
      - rateLimitByUser()    → Limite par utilisateur
      - authRateLimit()      → Strict pour auth (5 req/5min)
      - combinedRateLimit()  → Combinaison IP + Tenant + User
      - Headers: X-RateLimit-Limit, Remaining, Reset
      - Retry-After header quand limite atteinte

   B) Response Cache Middleware
      - responseCache()      → Cache réponses HTTP
      - Vary by tenant, user, query params, headers
      - TTL configurable
      - Cache-Control header support
      - X-Cache header (HIT/MISS)
      - Invalidation helpers:
        * invalidateCache()
        * invalidateTenantCache()
        * invalidateUserCache()

✅ 4. CACHE KEYS STANDARDISÉS
   - TenantCacheKeys (data, config, settings, limits, etc.)
   - UserCacheKeys (profile, permissions, session, etc.)
   - SessionCacheKeys (active, data, token)
   - RateLimitCacheKeys (byIp, byTenant, byUser)
   - ApiCacheKeys (response, pattern)
   - FeatureCacheKeys, BillingCacheKeys, WebhookCacheKeys
   - LockCacheKeys (distributed locks)

UTILISATION - EXEMPLES RAPIDES
================================================================================

1. CACHE SIMPLE
   ```typescript
   import { cacheService } from './cache/cache.service.js';

   // Set
   await cacheService.set('key', { data: 'value' }, { ttl: 300 });

   // Get
   const value = await cacheService.get('key');

   // Delete
   await cacheService.delete('key');
   ```

2. CACHE-ASIDE PATTERN
   ```typescript
   const user = await cacheService.getOrSet(
     'user:123',
     async () => prisma.user.findUnique({ where: { id: '123' } }),
     { ttl: 3600 }
   );
   ```

3. TENANT CACHE
   ```typescript
   import { tenantCacheService } from './cache/tenant-cache.service.js';

   // Get tenant (avec cache)
   const tenant = await tenantCacheService.getTenant(tenantId);

   // Increment API calls
   const count = await tenantCacheService.incrementApiCalls(tenantId);

   // Check limit
   const limitReached = await tenantCacheService.hasReachedApiLimit(tenantId, 1000);
   ```

4. USER CACHE
   ```typescript
   import { userCacheService } from './cache/user-cache.service.js';

   // Cache user profile
   await userCacheService.setUserProfile(user);

   // Check permission
   const canEdit = await userCacheService.hasPermission(userId, 'users.edit', tenantId);

   // Set online
   await userCacheService.setUserOnline(userId, 300);
   ```

5. RATE LIMITING
   ```typescript
   import { rateLimiterService } from './cache/rate-limiter.service.js';

   const result = await rateLimiterService.checkTenantRateLimit(tenantId, '/api/users');

   if (!result.allowed) {
     return res.status(429).json({
       error: 'Rate limit exceeded',
       retryAfter: result.retryAfter
     });
   }
   ```

6. MIDDLEWARE DANS ROUTES
   ```typescript
   import { responseCache, rateLimitByTenant } from './middleware/cache/index.js';

   // Cache response
   router.get('/courses',
     responseCache({ ttl: 300, varyByTenant: true }),
     async (req, res) => { /* handler */ }
   );

   // Rate limit
   router.post('/courses',
     rateLimitByTenant({ max: 100, windowSeconds: 60 }),
     async (req, res) => { /* handler */ }
   );
   ```

7. DISTRIBUTED LOCK
   ```typescript
   const lockValue = await cacheService.acquireLock('resource:123', 30);
   if (lockValue) {
     try {
       // Critical operation
       await performOperation();
     } finally {
       await cacheService.releaseLock('resource:123', lockValue);
     }
   }
   ```

BONNES PRATIQUES IMPLÉMENTÉES
================================================================================

✅ Fail Open Strategy
   - En cas d'erreur Redis, l'app continue de fonctionner
   - Rate limiting échoue en permettant la requête
   - Cache miss retourne null et charge depuis DB

✅ Cache Invalidation
   - Invalidation par pattern (deletePattern)
   - Invalidation par tenant/user
   - Invalidation automatique sur mise à jour

✅ Key Naming Convention
   - Préfixes standardisés (tenant:, user:, session:, etc.)
   - Namespaces pour organisation
   - Key generators réutilisables

✅ TTL Management
   - TTL configurables par type de données
   - Expiration automatique
   - Sliding windows pour rate limiting

✅ Security
   - Rate limiting strict sur auth endpoints
   - Blacklist/whitelist support
   - Distributed locks pour opérations critiques

✅ Monitoring
   - Cache statistics tracking
   - Hit rate calculation
   - Health check endpoints
   - Error logging

✅ Performance
   - Batch operations (mget, mset)
   - Pipeline support
   - Connection pooling
   - Cache warm-up on startup

✅ Scalabilité
   - Redis client singleton
   - Support pour Redis Cluster (configuration prête)
   - Support pour Redis Sentinel (HA)
   - Graceful shutdown
